D03

Promon 类方案的对抗思路

以“持续更新”的方式硬刚顶级检测

顶级检测壳的共同点是：它们把“检测”做成了产品，而不是补丁。

说人话

有些壳你绕过一次就再没遇到麻烦，有些壳每次更新都要重新打一遍——差别不在技术难度，在于对方有没有把它当产品在做。

做产品的会有版本迭代、会统计误报、会专门研究新的检测面。对这类对手，「彻底绕过」是个不现实的目标；现实的目标是「稳定待在它的判定线以下」。

所以这一章讲顶级方案的共同特征、这条思路的具体做法、以及为什么“持续演进”是唯一可持续的策略。

3.1 顶级方案的特征

  • 多进程协作：检测逻辑分散在多个进程，杀掉一个不影响其他。
  • 动态下发：规则可以远程更新，昨天有效的绕过今天可能失效。
  • 证明链优先：不依赖本地特征，依赖硬件证明（第 03 章）。
  • 行为基线：采集正常行为分布，偏离即报警（第 L09 章侧信道与结构差分检测）。

3.2 应对策略：从“绕过”到“共存”

当检测足够强时，“彻底绕过”往往不现实。更务实的思路是共存：让你的改动落在它不采集的维度上，而不是正面对抗。

思路做法适用
避开采样窗口在检测间隙完成操作短时操作
缩小改动面只改必要的一个点精准 hook
改变实现层从用户态转到内核态深度需求
接受部分暴露只保证关键能力可用长期维护

3.3 持续演进

顶级检测壳一直在更新，所以具体的“绕过步骤”很快就过期。可持续的方法只有一条：先建模型，再做实验，最后才谈对抗。任何“技巧”脱离模型都是不可复用的。

要点
这一章刻意写得“方法论”而不是“步骤”。因为壳在更新，具体步骤三个月就过期；而“先分层、再找成本边界、最后共存”这套思路，五年都不过时。

3.4 本章自测

  • 顶级检测方案的四个共同特征是什么？
  • 为什么“共存”比“绕过”更现实？
  • 四种应对思路分别适合什么场景？
  • 为什么方法论比步骤更保值？
说人话

检测逻辑不写死在安装包里，而是运行时从服务器取。你分析的那一份，明天可能就不是这一份了。

所以对抗从「破一次」变成「一直跟」。这一节讲这种形态下的节奏，读完你会把精力放在「怎么快速复现和验证」上，而不是追求一次搞定。

3.5 深入：为什么“动态下发”让对抗变成持久战

规则可以远程更新，意味着“今天有效的绕过，明天可能失效”。这让对抗从“一次性攻克”变成“持续维护”。理解了这一点，就会明白为什么方法论比技巧重要。

模式对抗形态应对
静态规则一次性找到即赢
动态下发持久战建立可持续的验证流程

3.6 实战：建立自己的“回归套件”

  • 固定一组设备与系统版本。
  • 固定一组测试用例（启动、登录、关键功能）。
  • 每次改动后跑一遍，记录“哪几项退化”。
  • 把退化项当作待办，而不是“偶发问题”。
说人话

一次性的检测，你破了就破了。产品化的检测不一样：它会更新、会换策略、会针对已知的绕过补新的判断。你面对的不是一份代码，而是一个持续在改的对手。

所以对抗的形态从「找漏洞」变成「维持平衡」：你得一直能改、一直能验，而不是一次搞定。这一节讲这种形态下的打法，读完你对「彻底绕过」这个目标会有一个现实的理解。

3.7 原理推演：为什么“产品化检测”难以被彻底绕过

因为产品化的核心不是“检测更强”，而是“迭代更快”。它可以每周更新规则，而你只能被动应对。在这种不对称下，“彻底绕过”在数学上不成立——你追不上它的迭代速度。

形态迭代速度对抗结果
静态 SDK随版本可绕过
动态下发每周持久战
服务端风控实时只能共存

所以务实的策略是“共存”：保证你的核心能力在“它不采集的维度”上稳定工作。

说人话

和一套产品化检测「共存」，不是一句话的事，得在几个维度上分别让步或对抗：功能、性能、可观测性、可维护性。这张表把这几个维度摆开。

它的用处是把模糊的「怎么共存」变成具体的取舍：每个维度上你愿意付多少，想清楚了，方案才落地。

3.8 数据细节：共存策略的四个维度

维度做法风险
时间在采样间隙操作窗口短
空间用不被扫描的内存形态兼容性
权限在内核态完成门槛高
身份复用合法进程受限
说人话

把检测拆到几个进程里，每个只干一小段，互相对答案。你想绕过，就得同时骗过所有进程，而且它们的通信你也得跟着伪造。

这一节讲这种结构的难点在哪。读完你会明白为什么单点突破在这里不成立，只能从「它们怎么对答案」这条线上找缝。

3.9 深入：为什么“多进程协作”难对付

因为杀掉一个进程，其他进程还在。而且它们之间可能通过 Binder、共享内存、甚至文件来互相监控——你对一个进程的改动，会被另一个进程发现。

架构杀一个的后果对抗难度
单进程检测停止低
多进程其他继续中
多进程 + 互监控立刻报警高

应对思路：不要“杀”，要“让它们都看到正常的结果”。这比“绕过检测函数”难，但更持久。

说人话

一种是整段换：把整个检测模块换掉。一种是换参数：逻辑不变，只调阈值和开关。前者动静大、后者难察觉。

这一节比较这两种。读完你观察一个方案时，会先判断它是哪一种——这决定了你该怎么跟。

3.10 深入：动态下发的两种粒度

粒度内容影响
规则级新增/修改检测规则无需发版
策略级调整阈值/开关快速试错

策略级下发最麻烦：它意味着“同一个版本，在不同时间可能有不同行为”。这让“复现问题”变得困难。

3.11 实战：把“共存”拆成可执行的动作

  1. 列出它的采集面（第一章的检测地图）。
  2. 找出“采集不到的维度”。
  3. 把你的改动迁移到那些维度上。
  4. 每迁移一项，用三组对照验证。

周一能跑的脚本，周三就不行了

周五下班前你把脚本跑通，截图存档，心满意足地关了电脑。周一回来复现，一切正常；周三再跑，同一个 APK、同一台机器、同一行命令，进程却在 attach 后三秒安静退出。你没改过任何东西——变的是它。规则包在后台被换了一版，采集面重排了一次，昨天还空着的那个维度今天开始采样了。这类方案最折磨人的地方不是强度，而是它把「绕过」变成了一次性的运气：你对抗的不是一个二进制，是一条会自己往前走的产品线。

所以现场的正确姿势不是继续调脚本，而是先把「它变了什么」记下来。桌上摆两台机器，一台断网跑离线基线，一台联网跑当前规则；两边同时记录 openat 命中的配置文件路径、每次检测的调用序列和时间戳。有了这组对照，你才能把「玄学失效」翻译成一句可验证的话：某个观测面从「不采」变成了「采」。

规则包落地的一拍一拍

  1. 服务端 → 对 规则包 → 按设备分组下发一个带版本号的策略文件（阈值、开关、采集面清单）→ 结果是同一版本的 App 在不同时间拥有不同行为。
  2. 壳的配置加载器 → 对 规则包 → 在启动早期 openat 读取并做签名校验 → 结果是把旧规则从内存里替换掉，磁盘上通常只留一个看不出含义的缓存名。
  3. 采集面重排器 → 对 六个观测面 → 按新清单决定这一轮采哪几项、采几次 → 结果是原本安全的那个维度突然开始上报，你的旧脚本正好落在那里。
  4. 主进程 → 对 守护进程 → 通过 Binder 或共享内存周期性互发心跳 → 结果是任何一方被杀掉或长时间不回应，另一方立刻把 risk 等级拉满。
  5. 守护进程 → 对 主进程的地址空间 → 只读地抽查几个关键结构 → 结果是它不需要注入你，也能发现「结构被改过」。
  6. 行为基线模块 → 对 正常用户的时延分布 → 长期统计后设 p99 门限 → 结果是哪怕所有静态特征都干净，只要你的路径比正常人慢一截，依然会被记一笔。

把「共存」拆成当天就能做的动作

  • 你 → 对 两台机器 → 一台断网固定规则、一台联网跟随更新 → 结果是拿到一份「规则版本 × 行为差异」的对照，而不是一句「今天又不行了」。
  • 你 → 对 采集面清单 → 每次实验先打印当前命中的观测面编号 → 结果是把绕过动作从「盲改」变成「只改没被采的那一项」。
  • 你 → 对 改动面 → 一次只动一个点，动完立刻跑三组对照 → 结果是失效时能立刻定位到是哪一步引入的，而不是把整个脚本推倒重来。
  • 你 → 对 实现层 → 把必须长期存在的逻辑从用户态迁到更贴近事实的层 → 结果是让「被检测的事实」本身合理，而不是让检测函数说谎。
  • 你 → 对 交付物 → 每次更新后重跑同一套用例并归档日志 → 结果是三个月后你还能回答「哪一版开始变的」。

可复现实验：抓住规则生效的那一刻

双机对照的最小记录脚本（host 端）
# 机器 A：断网，固定离线基线
adb -s SERIAL_A shell settings put global airplane_mode_on 1
adb -s SERIAL_A logcat -c && adb -s SERIAL_A logcat -v time > /tmp/A.log
 
# 机器 B：联网，跟随当前规则
adb -s SERIAL_B logcat -c && adb -s SERIAL_B logcat -v time > /tmp/B.log
 
# 两边都抓一次「读了哪些配置文件」
adb -s SERIAL_A shell strace -f -p $(adb -s SERIAL_A shell pidof TARGET) \
  -e trace=openat -o /tmp/A.open 2>/dev/null
 
# 对比差异：同一时刻，B 多读了哪个文件，就从哪个文件入手
diff <(grep -oE '[^/]+$' /tmp/A.open) <(grep -oE '[^/]+$' /tmp/B.open)

看到什么算成功：两台机器在同一操作下的 openat 序列出现一处稳定差异，且这台联网机器随后多跑了一次此前没有的采集动作——你就把「规则热更新」从一个概念变成了可指认的文件和时间点。看到什么算失败：两边日志几乎一模一样，说明这次失效跟规则无关，回去查是不是环境漂移（系统更新、SELinux 状态、frida-server 版本），别把环境问题误记成「壳变强了」。

档位规则来源行为特征可持续的对策
离线固定随包内置可复现、可穷举逐项建模，做完整检测地图
策略热更服务端下发阈值同版本跨天不同每次实验先记录规则版本
规则热更服务端下发采集面旧脚本突然命中双机对照找新增观测面
多进程互检进程间心跳杀一个立刻暴露让所有进程都看到正常事实
行为基线长期统计 p99静态全干净仍报警缩小改动面、控制时延
要点
这章最反直觉的一点：最稳的对抗不是让自己更隐蔽，而是让自己比正常 App 更正常。隐蔽是在跟特征名单赛跑，名单会变；正常是在跟结构事实对齐，事实不随版本变。这也是为什么「共存」比「绕过」更持久：你不再需要预测下一版规则，只需要保证自己落在它不采集、或者采集了也挑不出毛病的那一侧。

把双机对照的习惯带进 P01 和 P02：那边虽然不谈热更新，但同样要求「先建模型，再动手」。再往后 T03 会把这套对照变成一张必须填满数字的记录表——到时候你会发现，本章这句「让事实真的合理」正是那张表里每一项指标最终的判定标准。
