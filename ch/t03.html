T03

训练营三：做一次完整的“隐藏 → 检测 → 改进”循环

用三组对照，把主观感觉变成数据

这一节训练的不是技术，而是“用数据说话”的习惯。

3.1 任务目标

拿 T01 的靶场 App，加上一套检测（maps / 线程 / FD / ClassLoader 四项）。然后：采基线 → 注入 → 观测 → 隐藏 → 再观测，用一张表记录每一步的数字。

3.2 四步流程

采集脚本骨架
def snapshot(tag):
    return {
        'tag':   tag,
        'maps':  count_lines('/proc/self/maps'),
        'threads': len(os.listdir('/proc/self/task')),
        'fds':   len(os.listdir('/proc/self/fd')),
        'loaders': count_classloaders(),   # Java 侧
    }
 
rows = [snapshot('clean')]
# 注入 agent 后
rows.append(snapshot('injected'))
# 应用隐藏手段后
rows.append(snapshot('hidden'))

3.3 记录表（这就是交付物）

指标cleaninjectedhidden结论
maps 条目———接近基线才算合格
线程数———只降不升
FD 数———同上
ClassLoader 数———同上
要点
表里的横线要你自己填。填完之后你会发现一件事：有些指标你怎么改都降不下来——那些就是“结构性痕迹”，也是检测方最可靠的信号。这个认知比任何技巧都值钱。

3.4 判定标准

  1. 合格：四项指标里有 ≥3 项回到基线 ±10% 以内。
  2. 不合格：任意一项显著高于基线，且你无法解释原因。
  3. 无法改进：某一项无论怎么做都降不下来——把它写进“已知限制”，而不是假装不存在。

3.5 交付物

  • 填完的记录表（含每一步的操作说明）。
  • 一段分析：哪一项最难降？为什么？
  • 一份“已知限制清单”：哪些痕迹是你承认消不掉的。

3.6 自测

  • 为什么必须有“clean”这一列？没有它会怎样？
  • 如果某项指标降不下来，正确的做法是什么？
  • “基线 ±10%”这个标准合理吗？在什么情况下需要放宽？
  • 这份记录表能用来做什么（除了自测）？

你坐在机器前，手里是一张空白 CSV

你坐在机器前，手里有 T01 那个靶场 App、一张只有表头的 CSV、两个已经排好的终端窗口。左边窗口跑采集，右边窗口准备注入。这一节不教新招式，只逼你做一件多数人跳过的事：把「感觉变干净了」换成「四个数字各是多少」。表头写着 tag, maps, threads, fds, loaders，下面的格子全是空的，得你自己一格一格填出来。

先把纸笔放旁边，写下一个假设：「注入之后 maps 会多出若干匿名可执行段，线程数会多两三个，FD 会多一两个，ClassLoader 数不变」。然后严格按 clean → injected → hidden 三个标签各采三次，每次都冷启动。你会发现最难的不是隐藏，是让三次测出来的数字彼此对得上——环境漂移比任何对抗都更能毁掉一张表。

三次基线，一拍一拍采

  1. 你 → 对 进程 → am force-stop 后冷启动，等 SDK 初始化完成再采 → 结果是避开「检测代码自己改变被测量量」的自污染，拿到真正的 clean 基线。
  2. 你 → 对 `/proc/<pid>/maps` → 数行数，另外单独数 r-xp 且路径为空的匿名可执行段 → 结果是两个数字，后者往往比总行数更敏感。
  3. 你 → 对 `/proc/<pid>/task` → 数目录项 → 结果是线程总数；连采三次取中位数，别拿第一次的值当基线。
  4. 你 → 对 `/proc/<pid>/fd` → 数目录项 → 结果是 FD 数；注意采集脚本自己打开的文件也会算进去，要在读数前先关掉。
  5. 你 → 对 Java 侧 ClassLoader → 用 Java.enumerateClassLoaders 数实例 → 结果是 loaders 数；这一项对「谁注入了 dex」最敏感。
  6. 你 → 对 三次结果 → 取中位数写进 CSV 的 clean 列 → 结果是后面所有比较都有同一把尺子，而不是拿某一次 lucky run 当参照。

注入与隐藏之后，数字怎么变

  • 注入器 → 对 目标进程 → 映射 agent、起 JS 线程、接管若干信号 → 结果是 maps 多出匿名可执行段、线程数 +2~3、FD 数 +1~2，四项里通常三项同时动。
  • 你 → 对 injected 列 → 把四个数字抄进去，逐项算相对 clean 的增幅 → 结果是第一次把「有痕迹」变成可比较的百分比，而不是一句「明显多了」。
  • 隐藏动作 → 对 maps 与线程名 → 改映射名、改线程名、合并短命线程 → 结果是名字类痕迹下降，但条目数与线程数往往纹丝不动。
  • 隐藏动作 → 对 linker 账本与 FD → 补登记、关掉闲置 fd → 结果是一部分指标回到基线，另一部分怎么也降不下来。
  • 你 → 对 hidden 列 → 再采三次取中位数，与 clean 逐项对比 → 结果是表里最后两列终于可以填「合格 / 不合格 / 无法改进」了。

可复现实验：一条命令量出四个数字

host 端采集脚本（改 PKG 后直接跑）
PKG=com.example.range
PID=$(adb shell pidof $PKG | tr -d '\r')
 
for tag in clean injected hidden; do
  echo -n "$tag, "
  echo -n "$(adb shell wc -l < /proc/$PID/maps | tr -d ' '), "
  echo -n "$(adb shell ls /proc/$PID/task | wc -l | tr -d ' '), "
  echo -n "$(adb shell ls /proc/$PID/fd   | wc -l | tr -d ' '), "
  echo 'loader_count_from_frida'
  read -p '按回车采下一个标签...' _
done
 
# ClassLoader 数用 frida 补：
#   Java.perform(() => { let n=0;
#     Java.enumerateClassLoaders({ onMatch:()=>n++, onComplete:()=>send(n) }); });

看到什么算成功：三个标签各有一行、每行四个数字，且同标签连跑三次的中位数波动在 ±3% 以内；hidden 列里至少三项落回 clean 的 ±10% 区间。看到什么算失败：clean 列自己三次就差了 20%——那不是隐藏失败，是基线没稳住，回去检查是否每次都 force-stop、是否等够了 SDK 初始化、采集脚本自己有没有多开 fd；或者 hidden 列四项全降但 UI 仍报失败，说明检测还看了第五个维度，把它补进表头重跑一轮。

指标clean（中位数）injectedhidden判定档位
maps 条目填实测值通常 +5~12改名可降、条目难降接近基线才算合格
线程数填实测值通常 +2~3合并线程可降 1只降不升
FD 数填实测值通常 +1~2关闲置 fd 可回基线较易合格
ClassLoader 数填实测值可能 +1结构决定，多数降不了常落「无法改进」
匿名可执行段填实测值必然增加只能换映射方式结构性痕迹
要点
这章最反直觉的一点：最难消掉的不是 maps 里那个 so 的名字，是线程数。名字能改、路径能隐藏、账本能补，可「为了干活必须多起一个线程」这件事由架构决定，不由命名决定。填完表你会亲眼看到某一项无论怎么改都贴着基线之上不肯下来——那就是结构性痕迹，也正是检测方最可靠、最省钱的那一类信号。承认它、写进已知限制，比假装它不存在有用得多。

交付物清单（缺一项就不算完成）

  1. 填完的记录表：三个标签 × 四个指标 × 三次原始值，附每次的操作说明（改了什么、什么时候改的）。
  2. 增幅计算：injected 相对 clean 的逐项百分比，hidden 相对 clean 的逐项偏差，标出合格 / 不合格 / 无法改进。
  3. 一段分析：哪一项最难降、你试过哪几种办法、为什么都失效；要落到具体机制，不要写「因为比较隐蔽」。
  4. 已知限制清单：明确列出你承认消不掉的痕迹，并说明检测方若只盯这一项会怎样。
  5. 三次原始日志：冷启动 logcat、采集脚本输出、frida 的 ClassLoader 计数，供别人复跑。
  6. 一行回归结论：不注入时四个数字是否回到 clean——用来证明表里变化的确由你的动作引起。

这张表合上，三组训练就走完了完整的一圈：T01 造出可证伪的检测，T02 学会不靠硬读也能拿到事实，T03 把事实变成可度量的证据。回头翻 D01 的采样时间线、D03 的双机对照，你会发现它们全是这一张表的放大版；而 A01 的速查卡和 A05 的排错手册，正是为了让你在下一台陌生机器上，还能用同样的顺序把格子填满。
