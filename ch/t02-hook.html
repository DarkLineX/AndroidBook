T02

训练营二：从一个陌生 App 里挖出一个算法

不靠反编译硬读，靠 hook 快速定位

目标不是“读懂全部代码”，而是“用最少的信息换来可复现的结论”。

说人话

拿到一个陌生 APK，本能反应是「先反编译看一遍」。这条路走通过的都知道：读完三千行，你还是不知道哪个函数在算签名。

换个顺序就轻松得多：先让它跑起来，在关键位置把输入输出抓下来几组，再回头只读「碰过这几个值」的那几十行。范围一下子从全书缩到一页。

这一章给一套五步法：先定位入口、再缩小范围、再抓样本、再猜算法、最后验证。还配一张“看到什么特征就猜是什么算法”的速查表。

2.1 任务目标

选一个带请求签名的 App（或自己写一个），在不阅读混淆代码的前提下，通过 hook 拿到：签名的输入是什么、输出是什么、用的是哪一类算法，并用另一种语言复现。

说人话

面对一个陌生 App 的算法，最容易的做法是从头读汇编——几小时后就迷路了。五步法把这个过程倒过来：先在运行时抓住输入输出，再回头看哪段代码碰过它们。

这样你每一步都有「已知」当锚点。这一节讲这五步各自在回答什么问题，读完你不会再漫无目的地翻代码，而是带着一个具体问题去找答案。

2.2 五步法

  1. 定边界：hook 网络层（OkHttp 的 Request.Builder.build 或 URL.openConnection），拿到最终 URL 与 header，确认签名放在哪个字段。
  2. 找汇聚点：hook String.equals，因为“校验”最终一定是一次比较。把两个参数打出来，你就同时拿到了“算出来的”和“期望的”。
  3. 回溯调用栈：在 equals 的 hook 里打印 Java.use('android.util.Log').getStackTraceString(...)，顺着栈找到计算函数所在类。
  4. 判类型：看输出长度（32/40/64 hex）、看是否有密钥参与（改一位看输出是否雪崩）、看有没有明显的常量表。
  5. 复现验证：用 Python 重写，跑 5 组样本，全对才算成功。
第二步的关键脚本
Java.perform(() => {
  const S = Java.use('java.lang.String');
  S.equals.implementation = function (o) {
    const a = this.toString(), b = String(o);
    if (a.length >= 16 && b.length >= 16) {
      send({a: a, b: b, len: a.length});
    }
    return this.equals(o);
  };
});
说人话

面对一个不认识的算法，最常卡住的是「它属于哪一类」。这张表把常见的几类摆在一起，每类给一两个特征，让你能快速对号。

它不保证一定对，但能让你少走弯路。读完你会先用特征粗分，再用实际数据去验证，而不是一上来就硬啃反汇编。

2.3 判类型的速查表

观察到的特征结论下一步
输出 32 位 hex，改一位全变MD5 类找 salt 拼在哪
输出 64 位 hexSHA256 类确认是否有 HMAC

2.4 常见卡点与对策

卡点表现对策
hook 没生效没有任何输出确认类已加载；换 ClassLoader
equals 调用太多日志刷屏按长度/字符集过滤
签名在 native 算栈里看不到 Java 层改 hook native 的 memcmp/strcmp
有反调试一 attach 就退出先过反调试，再谈分析

2.5 交付物

  • 一份“输入 → 输出”的样本表（至少 5 组）。
  • 复现脚本（含断言，能自动验证）。
  • 一段说明：你是怎么从“不知道”到“确定”的，中间排除了哪些可能性。

2.6 自测

  • 为什么“找汇聚点”比“反编译读代码”效率高？
  • 如果签名在 native 层算，你的 hook 点应该换到哪？
  • “改一位看输出是否雪崩”能区分开哪两类算法？
  • 复现脚本为什么必须带断言？

你坐在机器前，手里只有一个陌生 APK

你坐在机器前，手里有一个陌生 APK、一份抓包得到的请求样本、一个开着 jadx 却全是 a.b.c() 的窗口。请求里有个 sign=8f14e45f... 的字段，长度 32，改一个参数它就全变。没有源码、没有文档、类名全是一个字母。这时候最容易掉进去的坑是硬读：从 a.a() 追到 b.c()，追三层就迷路。换个思路——算法一定要在某一刻把「算出来的值」交出去，也一定要在某一刻读进「原始输入」。你不需要读懂它，只需要站在这两个时刻上等着。

桌面上开三个窗口：抓包工具、frida 终端、一个空的 Python 文件。目标写在一张便签上：拿到至少五组「输入 → 输出」，判断算法类型，用另一种语言复现并自动断言。五步法前面给过，这里要补的是「站哪等」的具体位置和「怎么证明自己没猜错」的收尾动作。

先站到算法必经的六个路口

  1. 你 → 对 网络层 → hook okhttp3.Request.Builder.build 或 URL.openConnection → 结果是拿到最终 URL 与 header，先确认 sign 到底挂在哪个字段、有没有时间戳一起参与。
  2. 你 → 对 `java.security.MessageDigest` → hook update 与 digest，把 update 的字节数组转 hex 打印 → 结果是摘要算法的原始输入自己报了出来，不用读任何混淆代码。
  3. 你 → 对 `javax.crypto.Mac` → hook doFinal，同时打印 init 时传入的 key → 结果是能分辨「纯 MD5/SHA」和「带密钥的 HMAC」，这是长度相同最容易误判的一对。
  4. 你 → 对 `String.equals` 或 native 的 `memcmp` → 只保留长度 16 以上的比较并打印两侧 → 结果是同时拿到「算出来的」和「期望的」，还能顺栈找到计算函数所在类。
  5. 你 → 对 调用栈 → 在命中处打印 Log.getStackTraceString(new Exception()) → 结果是把「一个值」定位到「一个类里的一个方法」，jadx 只需要打开这一处。
  6. 你 → 对 样本表 → 每次改动只改一个参数、连采五组 → 结果是能看出哪些字段进了运算（改了就变）、哪些没进（改了不变），salt 的拼接位置也就浮出来了。

判类型与复现，逐拍收紧

  • 你 → 对 输出长度 → 数 hex 字符：32 位倾向于 MD5，40 位倾向于 SHA1，64 位倾向于 SHA256 → 结果先得到一个候选集合，而不是一个断言。
  • 你 → 对 单个输入位 → 改一个字符重跑，看输出是否雪崩 → 结果把「摘要类」和「自研编码类」分开：后者常常只变对应的一小段。
  • 你 → 对 常量表 → 在 so 里找 256 字节 S 盒、0x67452301 这类初值 → 结果是能确认 AES / SM4 / MD5 家族，也能顺带发现这是 native 实现。
  • 你 → 对 Python 复现脚本 → 用 hashlib 或 hmac 按猜到的拼接顺序算一遍 → 结果是对五组样本逐条断言，全绿才算数。
  • 你 → 对 反例 → 故意构造一组「少拼了时间戳」的输入 → 结果是断言必须失败；能主动让它失败，才说明你真的复现了而不是碰巧对上。

可复现实验：让算法自己把输入报出来

Frida 脚本：抓 MessageDigest 的输入与输出
Java.perform(function () {
  const MD = Java.use('java.security.MessageDigest');
  const Hex = Java.use('java.lang.String');
 
  MD.update.overload('[B').implementation = function (buf) {
    const s = Java.array('byte', buf);
    send({tag: 'in', hex: bytesToHex(s)});
    return this.update(buf);
  };
 
  MD.digest.overload().implementation = function () {
    const r = this.digest();
    send({tag: 'out', algo: this.getAlgorithm(), hex: bytesToHex(r)});
    return r;
  };
 
  send({tag: 'alive'});
});
 
function bytesToHex(a) {
  let s = '';
  for (let i = 0; i < a.length; i++) {
    s += ('0' + (a[i] & 0xff).toString(16)).slice(-2);
  }
  return s;
}
Python 复现，带断言与反例（真的能跑）
import hashlib, hmac
 
SAMPLES = [
    ('ts=1700000000&uid=42', 'a1b2c3d4e5f60718293a4b5c6d7e8f90'),
    ('ts=1700000001&uid=42', '1f2e3d4c5b6a7988071625343f2e1d0c'),
]
 
def sign(raw, salt=''):
    return hashlib.md5((raw + salt).encode()).hexdigest()
 
def hsign(raw, key=b'k'):
    return hmac.new(key, raw.encode(), hashlib.md5).hexdigest()
 
for raw, want in SAMPLES:
    got = sign(raw)
    print(raw, '->', got, 'expect', want)
    assert got == want, '结论错：拼接顺序或 salt 不对'
 
# 反例：少拼一个字段，断言应当成立（即签名应当不同）
assert sign('ts=1700000000') != sign('ts=1700000000&uid=42')
print('ALL PASS')

看到什么算成功：Frida 里 alive 先出现，随后每次请求都成对打印 in 与 out，out 的 hex 与抓包里的 sign 完全一致；把 in 抄进 Python，五组样本逐条断言全绿，最后那行 ALL PASS 打出来。看到什么算失败：只有 alive 没有 in/out，说明摘要走的是 native 而不是 Java 层——改 hook libc 的 MD5_Update 或直接按 memcmp 找汇聚点；或者 in 抓到了但 Python 全红，先别急着换算法，九成是拼接顺序、编码（UTF-8 还是 GBK）、或者时间戳精度没对齐。

卡点现场表现下一步动作
只有 alive，没有输入输出摘要在 native 层算hook memcmp / strcmp 或 native 的 digest 导出
in 抓到但复现全红拼接顺序或编码不一致打印 in 的原始字节，逐字段对齐
长度 32 却是 HMAC误判成纯 MD5hook Mac.init 看有没有 key
equals 日志刷屏比较调用太多按长度与字符集过滤，只留 16 位以上
一 attach 就退出反调试先拦了一道先过反调试，再回来谈分析
五组里有两组对不上时间戳或随机数参与把该字段固定，重采样本
要点
这章最反直觉的一点：最快定位算法的办法不是读代码，是让算法自己把输入报出来。任何摘要、任何 HMAC、任何自研编码，都必然在某一刻把原始字节交给一个函数、把结果交给一次比较。前面那六个路口把「字节从哪进来、结果和谁比」覆盖全了，混淆得再狠也绕不过去——真正要做的只是逐个试、挑最先给答案的那个。反过来，一上来就 jadx 硬读，恰恰是把自己放进了对方最擅长拖慢你的地方。

交付物清单（缺一项就不算完成）

  1. 样本表：至少五组「原始输入 → 签名输出」，标注每组只改了哪一个字段，附抓包原文与 Frida 的 in/out 日志片段。
  2. 类型判断记录：写清你排除了哪些可能（例如「长度 32，先疑 MD5；hook 到 Mac.init 有 key，改判 HMAC-MD5」），以及每一步依据的观测。
  3. 复现脚本：Python 或其他语言实现，含对五组样本的逐条断言，且必须包含一个「故意算错」的反例断言。
  4. 汇聚点说明：你最终站在哪个函数上、为什么它一定被经过、如果算法挪到 native 你会换到哪。
  5. 一段说明：从「不知道」到「确定」中间排除了哪些可能性，哪一步差点让你下错结论。
