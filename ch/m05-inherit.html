M05

硬件断点 Hook 与 Perf 生命周期

register_user_hw_breakpoint、pt_regs.pc、inherit、ptrace regset、task/perf/退出回收

不改一个字节，靠 CPU 的调试寄存器触发——最“干净”的 hook。

说人话

硬件断点是所有 hook 里最“干净”的一种：一个字节都不改。

它靠的是 CPU 自带的调试寄存器：你告诉 CPU“当地址 X 被访问时提醒我”，CPU 就在硬件层面帮你盯着，触发时直接陷入你的处理函数。代码原封不动，所以任何“代码完整性校验”都查不出来。

代价是：这种寄存器只有几个（通常 4~8 个），用完了就没了；而且它的生命周期很麻烦——进程 fork 了要不要继承、进程退出了怎么回收、被 ptrace 撞上了怎么办。这一章逐个讲。

5.1 五个阶段

  1. register_user_hw_breakpoint：注册断点（地址、类型、长度）。
  2. 触发：命中后进入异常处理，拿到 pt_regs。
  3. 回调：读寄存器、改 pc、或记录现场。
  4. inherit：设置是否对子线程 / 子进程继承。
  5. 回收：任务退出或 perf 关闭时必须注销。

5.2 四个必须处理的问题

问题表现对策
槽位有限只有 4~8 个，用完即失败合并断点、分级使用
多线程每线程独立 perf event限制线程数或用 inherit
pt_regs.pc改 pc 是重定向的关键注意 BTI / PAC
退出回收线程退出不回收到 perf挂 task exit 通知

5.3 优势与劣势

优势：目标代码段一个字节都不变，CRC 与反汇编比对全部通过。劣势：槽位稀缺，只适合“点”不适合“面”；而且 perf 子系统本身可被观测。

注册一个执行断点（示意）
struct perf_event_attr attr = {
    .type = PERF_TYPE_BREAKPOINT,
    .size = sizeof(attr),          // 别忘了，漏了直接 EINVAL
    .bp_type = HW_BREAKPOINT_X,    // X = 执行断点
    .bp_addr = target_addr,
    .bp_len  = HW_BREAKPOINT_LEN_4, // arm64 执行断点只接受 4
};
bp = register_user_hw_breakpoint(&attr, handler, NULL, task);
要点
bp_len 是最容易写错的一项：执行断点的长度不是“机器字长”。arm64 的执行断点只接受 4 字节（且地址要 4 字节对齐），x86 只接受 1 字节；填 sizeof(long) 会被 arch_build_bp_info 判为 -EINVAL，注册直接失败——而失败原因看起来像“参数不对”，很容易被误判成“槽位不够”。
要点
取舍：如果目标只在一处被调用，硬件断点是首选；如果需要覆盖大量调用点，还是得回到 Text Shadow（M03）。

5.4 本章自测

  • 硬件断点为什么“最干净”？
  • 槽位有限时你会怎么分配？
  • inherit 的坑在哪？
  • 线程退出不回收会发生什么？
说人话

监控可以只盯一个线程、只盯一个进程、或者盯整台机器。范围越大，看到的越多，开销和噪声也越大。

这一节讲这三种范围怎么选。读完你不会为了「看得全」把范围开到最大，结果被噪声淹掉真正的信号。

5.5 深入：perf event 的三种作用域

作用域注册方式适用
单任务绑定到某个 task精确，但要逐线程
单 CPU绑定到某个 cpu适合系统级观测
系统级所有 CPU开销大

硬件断点通常用“单任务”作用域，因为你要 hook 的是“某个进程的某个地址”。这也解释了为什么“多线程 App 会消耗大量断点槽位”。

5.6 实战：断点没触发怎么查

  1. 确认地址正确（是不是漏加了基址）。
  2. 确认作用域正确（是不是绑到了错的 task）。
  3. 确认断点类型（HW_BREAKPOINT_X 是执行，R/W 是读写）。
  4. 确认没有超出槽位上限（注册会返回 -ENOSPC）。
说人话

监控一个地址，通常的做法是改那儿的字节或改映射权限——改了就有痕迹，一比对就露。硬件断点不一样：它让 CPU 自己在访问这个地址时报告一声，内存里的内容一个字节都没动。

所以它干净，但也因此受限：能监控的地址只有很少几个，超了就得排队。这一节讲的就是这份干净和这份限制怎么配平。

5.7 原理推演：为什么硬件断点是“零侵入”

因为它把“监控”交给了 CPU 的调试单元，而不是修改代码或数据。目标进程的代码段、数据段都保持原样，任何“比对字节”的检测都无法发现。

方式改代码改数据可被 CRC 发现
inline hook是否是
GOT hook否是否（但页权限变）
硬件断点否否否

所以硬件断点是“最干净”的，代价是“能力受限”（只有几个槽位、只能监控特定地址）。

说人话

硬件能同时监控的地址只有很少几个，而且「执行」「读」「写」可能还要抢同一批槽位。这张表列了不同架构的槽位数和支持的类型。

它的用处是排计划：动手前先算「我需要几个槽」，超了就得合并监控范围，或者换一种方式。不先算，写到一半才发现不够。

5.8 数据细节：断点槽位与类型

架构槽位数支持类型
ARM644~8（实现相关）执行 / 读 / 写
x864执行 / 读 / 写 / IO

注意“执行断点”与“读写断点”可能占用不同的槽位资源。设计时要先算清楚“我需要几个”。

说人话

「继承」这个词听着像把所有设置复制一份给子任务，实际只继承一部分：监控哪些地址会带过去，但计数、状态这些不一定。

理解得不准确，就会出现「父任务能抓到、子任务抓不到」的怪现象。这一节把继承的边界划清楚，读完你能预判哪些场景需要手动补一次。

5.9 深入：inherit 到底继承什么

它决定“子任务是否继承父任务的断点”。如果开启，fork 出的线程会自动带上同样的断点；如果关闭，就得为每个线程单独注册。

设置子线程行为适用
inherit = 1自动继承线程多的场景
inherit = 0不继承精确控制

注意：inherit 对“新建线程”有效，对“已经存在的线程”无效。所以“晚注册”的断点覆盖不到老线程。

说人话

「把执行位置挪到别处」听起来只是改一个寄存器。可挪过去之后，栈对不对、参数还在不在、返回时回到哪，全都要能接上。

这一节讲这些隐性约束。读完你不会以为「改个值就完事」，而会先把「回来之后怎么继续」想清楚。

5.10 深入：改 pc 真正的约束是什么

这里要纠正一个常见说法：改 pt_regs->pc 之后是靠 eret 返回执行的，而 ERET 不是间接跳转，不做 BTI 落点检查——BTI 只约束 BR / BLR / RET 的目标。所以“改到一个没有 BTI 标记的地址就会触发 BTI 异常”这个说法并不成立。

真正要小心的是另外三条：

  1. 必须是合法指令边界：落到一条指令中间会直接跑飞。
  2. 不要跳进依赖 PAC 的返回序列：跳过 PACIASP、或落到 AUTIASP 之后，后面返回时签名校验会失败。
  3. 不要跳过函数序言：栈帧建立、被调用者保存寄存器的保存都发生在序言里，跳过它们后面就是脏值。
安全的改法
// 改到一个“函数入口”（序言之前、指令对齐）
regs->pc = (unsigned long)my_handler_entry;
// 若要跳到函数中间：先确认不跨序言、不破坏 PAC 配对

5.11 实战：断点回调里能做什么、不能做什么

操作能否原因
读寄存器能上下文可用
改寄存器能直接生效
睡眠 / 分配内存不能异常上下文
发信号谨慎可能死锁

一个字节都不改，CPU 自己会停下来

检测方把 .text 从头到尾 CRC 一遍，全过；反汇编比对也全过。而目标函数入口的 DBGBVR0_EL1 里已经静静躺着它的地址，DBGBCR0_EL1 配好了“执行、EL0/EL1、使能”。命中那一刻 CPU 抛同步调试异常，你在 pt_regs 里读走参数、把 pc 改成另一个地址，eret 之后函数像什么都没发生一样被重定向。代码段没有任何变化，变化的是 CPU 的比较逻辑。

这类 hook 属于 perf 子系统的 PERF_TYPE_BREAKPOINT：一个 perf_event 绑一个 task，内核在每次上下文切换时把该 task 的断点写进当前 CPU 的调试寄存器。于是生命周期不再只是“注册—回调”，还要管 fork 的 inherit、线程退出、文件描述符关闭与槽位归还——账本比 hook 本身长得多。

说人话

硬件断点是 CPU 自带的功能：你告诉它“盯着这个地址”，它跑到那儿就主动停下来通知你。好处是一个字节都不用改，代码段保持原样，CRC 查不出问题。

限制也很硬：这种“槽位”只有几个，用完就没了；每个槽能盯的范围还很小（ARM64 上只能盯 4 字节且要 4 字节对齐）。这五拍讲的是：怎么申请槽位、怎么填参数、触发之后回调里能做什么、以及进程退出时怎么把槽位还回去——不还，第二次就注册不上了。

从 attr 到回调的五拍

  1. 模块 → 对 perf_event_attr：填 type=PERF_TYPE_BREAKPOINT、bp_type=HW_BREAKPOINT_X、bp_addr、bp_len=HW_BREAKPOINT_LEN_4、size=sizeof(attr)，结果是一份内核能接受的描述；size 漏填直接 -EINVAL，这是最不像错误的错误。
  2. 模块 → 对目标 task：调 register_user_hw_breakpoint(&attr, handler, NULL, task)，结果拿到一个 struct perf_event，内核为它的每个线程在 DBGBVR/DBGBCR 上排布槽位；inherit 设为 1 时新建线程自动继承，否则只覆盖注册时那一个线程。
  3. CPU → 对取指地址：把当前 PC 与所有已使能的 DBGBVRn_EL1 比较，命中即抛同步调试异常，结果是控制流转进 do_debug_exception；这一步纯硬件完成，不读内存、不改代码、也不经过任何可 CRC 的字节。
  4. handler → 对 pt_regs：读 regs->pc、regs->regs[0..7]、regs->regs[30]（LR）记录现场，若要重定向就把 pc 写成目标地址，结果是 eret 后从新地址继续；目标是间接跳转落点时要确认首指令为 BTI/PACIASP，并处理好 PAC 签名的 LR。
  5. 回收路径 → 对 task exit notifier 与 perf 文件：unregister_hw_breakpoint 后 put_task_struct，结果是槽位归还给该 CPU；缺了这一步，进程早就没了，槽位还占着，下一次注册直接 -ENOSPC。
返回码触发条件真实原因处理
-EINVALattr.size 漏填 / bp_len 填 sizeof(long)arm64 执行断点只接受 4 且地址 4 字节对齐改 HW_BREAKPOINT_LEN_4 并对齐地址
-ENOSPC注册返回槽位不足该 CPU 仅 4~6 个 BRP，且被 perf/kgdb 占用合并断点、按重要性分级
-EBUSY同一 task 重复注册已有 perf event 占着同一地址复用已有 event 的 fd
-ESRCH目标线程已退出task 引用未 pin 住在 exit notifier 里同步回收
-EOPNOTSUPP内核无 HW breakpointCONFIG_HAVE_HW_BREAKPOINT 未开回退到 M03 的影子页

线程一多，账本就要加两列

register_user_hw_breakpoint 传进去的那个 task 只代表一个线程，不是整个进程。若目标开了八条线程，而 inherit 又没设，结果就是“主线程命中、其他七条照常跑”；把 inherit 打开能让新建线程继承，但已经存在的线程不会补登记，仍要遍历线程组逐个挂 event。于是每个断点要记的不只是地址和 slot，还得记“绑到了哪个 task、什么时候由谁回收”。

上下文切换是另一处容易误判的地方：DBGBVR/DBGBCR 是 per-CPU 寄存器，调度器把待运行 task 换上 CPU 时才把它的断点写进当前核的寄存器组。所以“注册成功”不等于“此刻硬件里就有值”——线程被调度上来之前，槽位只是 perf 账本里的一行记录；slots_in_use 与“当前核实际生效的槽位”是两个数，验收时要分开看。

槽位不够时怎么分

  • 先合并同地址：多个模块盯同一个函数入口就共用一个 event，用回调链分发，结果是省下整一个槽位；inherit 打开的线程组只算一份配置，不按线程数重复申请。
  • 再按优先级降级：只给关键入口留执行断点，次要观测点退回 M03 的影子页或 kprobe，结果是有限的 BRP 全落在绕不开的点上。
  • 最后留出诊断位：至少保留一个槽位给临时排查，否则一旦四个全被占满，连“为什么注册失败”都没法现场验证，只能重启。

可复现实验：注册、触发、杀进程、数槽位

四段对账，最后一段最容易被漏掉
# 1. 先探测支持与当前占用
zcat /proc/config.gz | grep -E 'CONFIG_HAVE_HW_BREAKPOINT|CONFIG_PERF_EVENTS'
cat /proc/kallsyms | grep -E ' register_user_hw_breakpoint| hw_breakpoint_add'
# 成功：两项均为 y 且符号存在；失败：=n 或无符号，改走 Text Shadow
 
# 2. 注册一个执行断点（bp_len 必须是 4，地址 4 字节对齐）
insmod /data/local/tmp/hwbp.kpm pid=$PID addr=0x7f00123400
dmesg | tail -n 20
# 成功：打印 bp slot 0、hw_bp_enabled=1；失败：-EINVAL 先查 bp_len，-ENOSPC 查槽位
 
# 3. 触发并观察重定向
cat /proc/demo/hwbp_stats
# 成功：hits 递增且 redirected 与 hits 相等；失败：hits=0 = 地址错或 inherit 没覆盖子线程
 
# 4. 强杀目标进程后核对回收
kill -9 $PID
sleep 1
cat /proc/demo/hwbp_stats
# 成功：slots_in_use 回到 0；失败：仍非 0 = exit notifier 没挂上，槽位泄漏
要点
最反直觉的一点：硬件断点最“干净”，却不是最隐蔽。它确实一个字节都不改，CRC 与反汇编比对全过；但 perf_event 会出现在 fdinfo 与 perf 子系统的账本里，调试槽位的占用也能被同级内核读到，上下文切换时写 DBGBVR 的开销还是可测的。“不改字节”只骗过校验代码，骗不过看账本的人。

把三种入口改控制流的方式并排看：Frida 部 F06 讲默认 Hook 时用 trampoline 覆盖入口指令，LSPosed 部 L02 讲 LSPlant 时改写 ArtMethod 的入口与 backup，M05 则把地址交给 CPU 的调试寄存器。手段从“改字节码”一路退到“只改配置”，但三者面对的是同一个工程问题：注册、生效、并发、撤销，四步一步都不能少。
