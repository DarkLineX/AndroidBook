A04

附录 D · 全书自测参考答案

先自己做，再对照

答案给的是“要点”，不是“标准作文”——能覆盖这些要点，就算掌握。

D.1 第一部（01–16）

01 APatch

  • boot.img 五段：header / kernel / ramdisk / second-dtb / AVB footer。
  • 改 kernel 更隐蔽，是因为载荷运行在 EL1，不受 SELinux 与 capability 的常规约束；ramdisk 的东西仍在用户态。
  • AVB 失败会拒绝启动或降级；两种处理：关掉校验（重刷 vbmeta 带 disable 标志）或重新签名。
  • 单靠 APatch 拿不到 STRONG——STRONG 看的是硬件证明与 boot 状态，不是“有没有 root”。

02 启动链

  • 八步：BootROM → abl → boot.img → kernel → init → zygote → system_server → App。Java 世界从 zygote 开始。
  • GREEN 可满足 STRONG；YELLOW 通常不行；ORANGE 只能 BASIC；RED 拒绝启动。
  • fork 之后、降权之前仍是 root 身份，能读 /data/adb，此时还没有 App 的身份约束。
  • 若在 init 阶段就被注入，App 在 attachApplication 时会看到“多出的线程 / 匿名映射 / 异常 ClassLoader”。

03 硬件证明

  • Normal World / Secure World；TEE 有独立内存与页表，普通世界无权访问。
  • verifiedBootState、deviceLocked、osVersion、osPatchLevel、verifiedBootKey（+ verifiedBootHash）。
  • 解锁但未 root：通常拿得到 BASIC 与 DEVICE，拿不到 STRONG。
  • 除证书内容外，还应查：时延分布、离线行为、多应用一致性、verifiedBootHash 与本地 vbmeta 是否一致。

04 root 检测

  • 应用层最易绕；硬件层最难绕。各自短板见 4.2。
  • 因为差分测的是“关系”，不依赖具体特征，改名换工具都无效。
  • 先在 SDK 初始化完成后采基线，之后只比较增量，并设 p99 阈值。
  • 建议保留：结构层、内核层、硬件层（三层互相独立，难以同时伪造）。

05 App 启动

  • 预加载 framework 类、资源、以及 zygote socket；所以一次注入全部继承。
  • attachApplication 在前（注册 ApplicationThread），bindApplication 在后（创建 Application）。
  • 因为 dexElements 是类查找路径，插入新 dex 就能让新类被优先找到。
  • 会失败——Java.use 走默认加载器，找不到由其他 ClassLoader 加载的类。

06 linker

  • dlopen → mmap 各 PT_LOAD → 解析 DT_NEEDED → 重定位 → init_array → JNI_OnLoad。
  • RELATIVE 是“基址 + 加数”，GLOB_DAT 是“查符号表得到的地址”。
  • 匿名可执行段意味着“代码没有对应文件”，正常 so 不会这样；正当场景：JIT 缓存、部分图形库。
  • TLS 重定位、BTI/CFI 标记、卸载清理。

07 ptrace

  • 最容易失败的是“算 dlopen 地址”和“恢复现场”——前者错就跳飞，后者错就崩。
  • detach 只清零 TracerPid，注入留下的映射、线程、solist 项都还在。
  • 0 = 任意进程可 attach；1 = 只能 attach 后代或经 PR_SET_PTRACER 授权；2 = 仅管理员。
  • 会失败：64 位系统上 32 位注入器无法正确操作 64 位进程的寄存器与地址空间。

08 zygisk

  • 因为所有 App 都是 zygote 的 fork 产物，已加载的代码与已改的指针会被继承。
  • pre 能读 /data/adb 但不知自己是谁；post 知道自己是谁但读不到模块目录。
  • dev/inode 与原厂不一致、mountinfo 多出 bind 记录。
  • 选“能覆盖目标场景的最晚时机”——越早越干净但越脆弱。

09 hook

  • 因为 so 内部调用直接跳到函数地址，不经过 GOT/PLT。
  • 指令边界、并发安全、PC 相对寻址、指令缓存刷新。
  • BTI 是间接跳转目标校验；桩函数不带 BTI 标记，通过 BR/BLR 到达时会触发异常。
  • 同时查 CRC 与页权限时，可改用硬件断点（不改字节、不改权限）。

10 Frida

  • Device 管连接、Session 管进程、Script 管代码。
  • 已注入的 agent 会失联（消息无法中转），但目标进程内的 hook 仍在运行。
  • 因为 send 是“唯一能证明脚本真的执行了”的信号，print 可能被缓冲或丢弃。
  • 卡在注入层：权限（SELinux）/ ptrace / 目标进程状态。

11 注入检测

  • 最难伪造的是“行为时序”——它由真实执行路径决定，改不了。
  • 因为字符串可以被加密、拆分、或干脆不出现；未命中不能证明清白。
  • 例：① 无网络的 App 却有 8 个线程；② maps 匿名可执行段是基线 2 倍；③ ClassLoader 的来源路径指向私有目录。
  • 自污染 = 检测代码自己改变了被测量的量；解法是先初始化再采基线。

12 Java Hook

  • resolve 出 ArtMethod → 读 entrypoint → 跳转。
  • 因为桩是 native 实现，ART 必须按 JNI 约定调用它。
  • 因为调用者里已经是内联后的指令，不会再看 entrypoint；解法是 deopt。
  • 查 Method.getModifiers() 是否多了 native，以及 dex 来源是否异常。

13 IPC

  • App → libbinder → binder 驱动 → system_server。
  • 因为还有包管理视图、进程视图、服务注册表三本账。
  • 文件视图 / 包管理 / 进程 / 服务表。
  • 调用会失败并抛异常（服务不存在或权限拒绝）。

14 dex

  • header / string_ids+type_ids / proto_ids+field_ids / method_ids / class_defs / data。
  • 因为业务 dex 往往在“某个类被加载”后才解密出来。
  • 在“回填完成、方法即将执行”的那一刻。
  • header 的 size/offset、checksum、map_list、class_def 顺序。

15 自动化

  • u2 走控件树，scrcpy 走画面流，两者并列而非串联。
  • 因为 sleep 无法区分“慢”和“坏了”；应改成条件等待 + 超时。
  • 页面签名 = 本页必然存在的若干元素组成的集合，全部命中才算到页。
  • 先统计失败集中在哪一步、哪类设备，再看是元素定位问题还是时序问题。

16 脚本与算法

  • 见 16.1 的两个脚本。
  • 定边界 → 找汇聚点 → 判类型 → 复现 → 落脚本。
  • 因为很多“分析失败”其实是 hook 没挂上，分析的是原逻辑。
  • 例：“这是 MD5”——构造已知输入比对输出，对不上就说明结论错。

D.2 第二部（K01–K08）

K01 进程与调度

  • 共享 mm/files/sighand 与否；线程就是带 CLONE_VM|CLONE_FILES|CLONE_THREAD 的 task。
  • 因为复制的是表与指针（COW），不是物理内存。
  • uid 家族、gid 家族、capabilities、SELinux SID；提权改 uid 与 cap。
  • 因为 MDSCR_EL1 是每核寄存器，迁移会打乱状态。

K02 内存

  • VMA 是“一段虚拟区间”的描述，页表是“逐页翻译”的实现。
  • 因为 CPU 会缓存翻译结果，不刷就还在用旧的。
  • 代价是写时复制会触发缺页，产生额外开销。
  • rmap、RSS 计数、GUP 路径。

K03 异常

  • 同步异常由指令触发，异步中断由外部事件触发。
  • 改 pt_regs->pc。
  • MDSCR_EL1.SS 与 SPSR_EL1.SS。
  • 因为单步改变时序，可能让超时判断、握手流程走不同分支。

K04 VFS

  • fd 是索引，file 是打开实例，inode 是文件本体。
  • 因为内核不能分配“可能很大”的缓冲，只能分段生成。
  • dev/inode 与原厂不一致、mountinfo 多出 bind。
  • 能——inode 号相同但内容被换，需要靠内容哈希或类型策略发现。

K05 追踪

  • ftrace 是函数级追踪，kprobe 是任意位置插桩（可读写寄存器）。
  • 因为它在崩溃时把日志写进持久存储，重启后还能读。
  • 能告诉你“哪里热”，不能告诉你“为什么热”。
  • 换 tracepoint，或提高 printk 级别，或改用 pstore。

K06 BTF

  • BTF 只保留类型结构，DWARF 还含行号/宏等调试信息。
  • 因为 CO-RE 需要在运行时按 BTF 求值“偏移表达式”。
  • 编译期要有头文件；BTF 要有 /sys/kernel/btf；扫描要验证。
  • 用 System.map + 特征扫描，或做运行时探测。

K07 符号

  • 运行地址 = 链接地址 + slide。
  • 因为 KASLR 只平移整个镜像，不改变镜像内部的相对距离。
  • KMI 是符号白名单 + ABI 签名；MODVERSIONS 是装载期的 CRC 校验。
  • 先读 /proc/kallsyms 与 BTF 是否存在，再判断走哪条定位路径。

K08 SELinux

  • DAC 看 uid，root 可绕；MAC 看域与类型，root 绕不过。
  • scontext=主体域，tcontext=客体类型，tclass=客体类别。
  • 说明系统在 permissive 模式，只是记录不拦截；切回 enforcing 就会失败。
  • 因为判定依据是“域”，不是 uid。
  • 若要“不被发现”选换路径；只要“跑通”可以改策略。

D.3 第三部（F01–F11）

  • 五层：host 工具 / server / 注入器 / agent / 脚本。
  • spawn 会暂停在入口等脚本；attach 只能介入已在运行的进程。
  • 解决“反调试在启动最初几百毫秒内完成”的问题。
  • 理论上可以，实际上很难——agent 的映射与线程总会留下统计特征。
  • 因为 Java.perform 是异步排队的。
  • 保证 JavaVM 可用与 ClassLoader 可用；不保证目标类已加载。
  • 传输 / server 存活 / 注入 / 脚本逻辑。
  • 因为每条消息都要经 server 中转。
  • DAC 与 MAC 两套；frida 需要 ptrace/setcontext/file 等权限。
  • 策略文件变化、/sys/fs/selinux 状态、avc 日志消失。
  • 换路径（内核态完成，见 M06）。
  • 线程注册表、模块注册表、信号接管、退出监控、子进程门控。
  • 因为它们是“无论写什么脚本都会发生”的副作用。
  • 单点 inline hook + 自有线程 + 不做信号接管。
  • 失去拦截目标 fork 出的子进程的能力。
  • 翻译后再执行（接近原生），不是逐条解释。
  • 因为 B 指令只有 ±128MB 范围。
  • 匿名可执行页、跳转密集、速度骤降、线程被暂停。
  • 短时定点用；长期监控不用。
  • 线程名、线程数、start_routine、栈分布。
  • 因为它是“创建时传入的真实地址”，不能随便编。
  • 创建后立刻改；验证方式是高频轮询看有没有捕获到默认名。
  • PT_LOAD 映射、重定位、init_array、TLS（额外）；还有卸载。
  • 因为它需要“初始化 TLS 模块”这一步，最小实现常省略。
  • 间接调用目标缺 BTI 标记，触发异常。
  • 能 mmap 各段、能处理 RELATIVE、能调用一个导出函数、能卸载。
  • start_routine 指向匿名映射。
  • TLS 里的线程链表（libc decoy）。
  • 备份、改、校验。
  • 因为栈地址能反映“这个线程从哪来”。
  • maps 过滤 / linker 账本 / CFI shadow / 匿名映射 / Instruction.parse / 线程名 / FD / 信号。
  • maps 过滤、linker 账本、Instruction.parse 可读性（互相牵制）。
  • 因为它提供了“同机型同版本”的对照基准。
  • 代码段被映射成 --x（只执行不可读）时读取失败；解决是保证映射可读。
  • 源码、构建脚本、验证脚本、基线数据、已知限制清单。

D.4 第四部（M01–M07）

  • 因为它绕开了签名、vermagic、MODVERSIONS 三道关。
  • 卸载期的残留崩溃（地址已释放但 timer 还在跑）。
  • 把“申请与释放”成对登记，避免遗漏。
  • 因为释放顺序要与申请顺序相反，否则会用到已释放的资源。
  • map_files / statx 能揭示“内容与身份不符”。
  • 读不触发崩溃、不改变状态、不留“被改过”的痕迹。
  • 表项地址与 kallsyms 期望值不一致。
  • 先 dump 实际表结构，再写读取代码。
  • 必须复制页，否则改动会被所有映射它的进程看到。
  • 因为 CPU 缓存了旧翻译。
  • 要重算 PC 相对寻址的偏移。
  • rmap 不维护→回收崩溃；RSS 不维护→统计被差分抓；GUP 不维护→数据不一致。
  • MDSCR_EL1.SS、SPSR_EL1.SS、KDE（通常已置位）、CPU 亲和性。
  • 异常上下文不能睡眠，重活会卡死系统。
  • 会让时序敏感代码走不同分支。
  • 先用 kprobe 粗定位，再对那一小段开单步。
  • 因为不改字节、不改权限，CRC 与反汇编比对都通过。
  • 优先给“调用频率高、价值大”的位置。
  • inherit 对已存在线程无效。
  • perf event 泄漏，最终耗尽资源。
  • 因为 avc_denied 是“拒绝路径上唯一能翻成放行”的拦截点。
  • 前者是进程上下文，后者是客体（文件/socket）上下文。
  • 改判定的痕迹是“策略应拒却允许”；换域是“操作发生在有权限处”。
  • 先用缓冲区不足的方式探测返回长度，再分配。
  • 看 dmesg 的 avc 日志，逐字段对照 allow 规则。
  • 因为 UID 不同才有独立沙箱与独立存储。
  • CE 需解锁后可用，DE 开机即可用。
  • 因为半改状态最难恢复。
  • 并发登录、强杀隔离、无残留、可回滚。

D.5 第五部（L01–L10）

  • pre 读配置进内存，post 按包名/UID 决定用不用。
  • 因为 post 阶段已降权，读不到 /data/adb。
  • 沙箱内 App 却访问过 /data/adb、framework dex 的匿名映射、dexElements 多出条目。
  • 会跳过注册，表现为“模块对该进程不生效”。
  • 定位 ArtMethod、生成桩类、写蹦床、替换 entrypoint、备份原方法。
  • 因为要处理 kAccNative、参数类型、调用约定。
  • 还在（如果桩正确保留了 synchronized 语义）；处理不当会丢锁。
  • 方法变 native、dex 来源异常、调用耗时异常。
  • 按 priority 排序；顺序错会导致语义错。
  • 因为内联后调用者不再看 entrypoint。
  • 性能骤降、时序改变。
  • 因为“突然变慢”本身就是异常。
  • 先父后子，保证核心类不被覆盖。
  • SharedMemory（隐蔽）、file-backed（简单）、内存 dex（兼容差）。
  • 因为不在同一条委派链上。
  • 还有对象持有模块类的引用。
  • 编译期常量最难（要改构建）、IR 改写最深。
  • 因为运行时抹字符串说明它曾经存在过。
  • 用枚举值承载语义，名字延迟绑定。
  • 一体两面：混淆让逆向难，泛化让检测难。
  • Binder / FD / linker / module counter。
  • 因为其他线程可能正在遍历，写错就踩空。
  • 能发现“只改了一半”的不一致。
  • 因为死亡通知也体现了“这个代理存在过”。
  • 因为动态类不在 dex 里，反射枚举看不到。
  • 因为备份与本体温差明显，容易被扫出来。
  • 因为 ART 可能返回包装对象以支持通用 API。
  • 因为厂商定制会让 “版本号” 与 “实际行为” 不一致。
  • 因为对象会移动，裸指针失效。
  • 把版本相关代码集中，上层只依赖适配层。
  • 选 3~4 个有代表性的（最老/主流/最新）。
  • 因为 GC 可能移动或卸载它们。
  • 时延分布最难（由真实执行路径决定）。
  • 因为它测的是统计性质，不依赖具体特征。
  • 因为不同版本的性能差异远大于 hook 带来的开销。
  • 让结构真的变合理——没有捷径。
  • 基本 Hook、冷启动、full GC（最易被忽略）。
  • 因为不写限制，下一个人会反复踩同一个坑。
  • 可信链、运行链、检测链。
  • 开放题：建议选“三绿 + 注入检测”的组合，因为它同时覆盖硬件层与结构层。
要点
这份答案的用法：先自己答，再对照“要点是否覆盖”。不要背原文——技术细节会随版本变化，能自己推导出来才算真的掌握。

答案都对上了，却说不出为什么

你翻到 D.1，把第 04 章那四道题对照一遍，发现要点全中，心里松了一口气。可合上书，有人问「为什么差分检测改名换工具都无效」，你张了张嘴，只能把答案里的句子复述一遍。这是最危险的一种「掌握」：记住了措辞，没建立起能推导的机制。前面那五大部分给的是要点，不是作文模板；这一页要补的是「怎么使用答案」，以及怎么把一句要点升级成一条可证伪的陈述。

拿一张卡片，正面抄题目，背面只写三样东西：一个能跑的最小实验、一个预期现象、一个能让这条结论失效的反例。写不出第三样，就说明还没真懂，回去重做那一章的实验，而不是再背一遍。

把「要点」升级成「可证伪陈述」

  1. 你 → 对 一条答案要点 → 先问「它断言了什么关系」→ 结果是把陈述句改写成「若 A 变，则 B 必变」的形式，含糊的词自动暴露。
  2. 你 → 对 改写后的断言 → 设计一个十行以内能跑完的实验 → 结果是要点从文字变成可执行动作，例如「改线程名」对上「差分检测仍报警」。
  3. 你 → 对 实验结果 → 记录预期现象与实测现象 → 结果是一致才算暂时成立，不一致就回去修模型，而不是修措辞。
  4. 你 → 对 反例 → 主动构造一个「应当让结论失效」的场景 → 结果是能说出「在什么条件下这条不成立」，这才是边界。
  5. 你 → 对 卡片背面 → 把实验、现象、反例三行写满 → 结果是复习时不用重读章节，跑一遍脚本就能自检。
  6. 你 → 对 整章 → 隔一周随机抽三张卡重跑 → 结果是记得牢的是能复现的那几条，背过的那几条会先漏，正好知道该补哪。

四档掌握度，逐拍对号入座

  • 第一档 · 认得：看到答案能点头，但说不出机制 → 结果是遇到变种题就卡住，属于「读过」不是「会」。
  • 第二档 · 复述：能把要点完整背出来 → 结果是面试够用、现场不够用，因为真实环境不会按措辞出题。
  • 第三档 · 复现：能独立写出最小实验并跑出预期现象 → 结果是结论有了证据，换台机器也敢下判断。
  • 第四档 · 证伪：能主动造出反例、说清结论的适用边界 → 结果是版本变了、样本换了，你依然能重新推一遍。
  • 判定：任何一道题若写不出反例，一律按第二档处理，别给自己放水。

可复现实验：把自测题做成抽卡脚本

真的能跑的 python（自建题库 + 掌握度记录）
import json, random, pathlib
 
CARDS = [
  {'q': '为什么差分检测改名换工具都无效？',
   'e': 'frida 注入后改线程名，再跑一次结构差分',
   'x': '仍报警',
   'r': '只看绝对特征名，且所有特征同时被抹成一致时才可能漏'},
  {'q': '抽取型壳该在哪一刻 dump？',
   'e': 'hook 目标方法首次执行，回调里按 DexFile 整段读',
   'x': 'jadx 能打开且关键方法有 invoke 指令',
   'r': '一代整体加密壳：启动时抓就够，不必等首次执行'},
]
 
db = pathlib.Path('mastery.json')
score = json.loads(db.read_text()) if db.exists() else {}
c = random.choice(CARDS)
print('题：', c['q'])
print('实验：', c['e'], '｜预期：', c['x'])
ans = input('能写出反例吗(y/n)：').strip().lower()
score[c['q']] = 4 if ans == 'y' else 2
db.write_text(json.dumps(score, ensure_ascii=False, indent=2))
print('当前档位分布：', {k: list(score.values()).count(k) for k in (2, 4)})

看到什么算成功：脚本随机抽题、打印实验与预期，你能在不看答案的情况下写出反例并输入 y，mastery.json 里该题被记为 4；隔一周重跑，同一题仍能拿到 4。看到什么算失败：每次都输 n，或者写出的「反例」其实只是把答案换了个说法（例如把「差分看关系」改写成「差分不只看名字」）——那还是第二档，回去把实验真跑一遍，别在文字里打转。

档位典型表现遇到版本变化建议动作
认得看到答案能点头完全卡住重读章节 + 跑一遍示例
复述能完整背出要点勉强套用、常出错给每条要点配一个最小实验
复现能跑出预期现象换机器仍可判断补写反例，找适用边界
证伪能造出让结论失效的场景能重新推导抽卡自测，隔周回归
伪掌握措辞流利但写不出反例最危险一律降回第二档处理
要点
这章最反直觉的一点：能背出答案，通常只说明你记住了措辞；能设计出一个让答案失效的反例，才说明真懂。因为答案描述的是「在正常条件下成立」，而现场永远在边界上。反例不是抬杠，它是你给结论划的那条适用范围——写不出来，就等于不知道自己什么时候会错。

这套「要点 → 实验 → 反例」的用法，跟 T01 先让检测正常失败、T02 故意构造算错的一组、T03 承认消不掉的痕迹，是同一套习惯的三种写法。全书到这里的答案不再是终点：翻回 A01 用症状定位、A05 用五层排错，你手里的就不再是六十五章的结论，而是一套能自己重新推一遍的方法。
