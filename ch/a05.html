附录 E · 常见问题与排错清单

90% 的“不工作”，都能在这几页里找到答案

按“症状 → 可能原因 → 排查动作”组织，遇到问题直接查。

说人话

这一页收的是排错顺序，不是排错知识。

为什么强调顺序？因为着急的时候人的本能是“同时改三个地方”，结果现象一变就再也不知道是哪个改动起的作用了。这一页给的是“先做什么、再做什么”的固定顺序，让你在最慌的时候也有章可循。

用法：按“症状 → 可能原因 → 该敲什么命令”三列查。查到之后一次只改一处，改完立刻重跑。

说人话

出问题时最耗时的不是修，是「不知道从哪开始查」。这张表就是给这个时刻用的：按顺序问几个问题，每个问题都能用一条命令回答。

三分钟内你能把范围缩小到某一层。这一节讲这张表怎么用，读完你遇到「什么都没反应」时，会先照表走一遍，而不是乱试。

E.5 一张“三分钟自检表”

  1. 设备能 adb shell 吗？→ 不能就先解决连接。
  2. getenforce 是 Enforcing 吗？→ 是的话所有跨域操作先想 SELinux。
  3. frida-ps -U 能列进程吗？→ 不能就是 server/端口/权限问题。
  4. 脚本里有 send('alive') 吗？→ 没有就先加，否则无法判断是否执行。
  5. 目标类真的被加载了吗？→ 打印 ClassLoader 与类名确认。
  6. dmesg 里有新报错吗？→ 有就先读它，比猜快十倍。
要点
最后一条最重要：先读日志，再改代码。绝大多数“玄学问题”，答案都躺在 dmesg 或 host 端的 error 里。

周五晚上，脚本突然一个字都不吐

周五晚上，离收工还有二十分钟，昨天还好的脚本今天一个字都不吐。终端安静得可疑：frida 连上了，进程也在，但回调一次没进。你第一反应是改脚本——加个 log、换个 hook 点、再改一次——三处一起动，改完现象变了，却更不知道是哪处起的效。前面 E.1 到 E.4 已经按环境、Hook、脱壳、内核分过类，E.5 给了三分钟自检表。这一页把那几张表摊成一条自上而下的五层二分：每层只问一个问题，看到什么算通过，不通过就停在这一层，绝不往下改代码。

把两只手从键盘上拿开，先念一遍顺序：连接 → server → 注入 → 脚本 → 目标逻辑。九成的「玄学」都卡在前三层，而人总爱直接冲到第五层。按这个顺序走，二十分钟够你把范围缩到一行命令上。

说人话

排查的本质是不断对半砍：先判断「问题在应用层还是系统层」，再在那一半里继续分。每砍一次，可疑范围就小一半。

关键不是砍得快，而是每次砍的依据要硬——能用一个现象证明「不在这边」。这一节讲这个流程，读完你不会再凭感觉猜，而是每一步都留下一条排除理由。

五层二分，逐拍往下走

  1. 第一层 连接 → 你 → 对 adb 通道 → 敲 adb devices 与 adb shell echo ok → 结果通过是状态 device 且回显 ok；不通过就先 adb kill-server、重插线、看设备端授权弹窗，此层不解决绝不往下走。
  2. 第二层 server → 你 → 对 frida-server 进程与端口 → adb shell ps -A | grep frida 加 adb forward --list → 结果通过是进程在、转发规则在、frida-ps -U 能列出目标 pid。
  3. 第三层 注入 → 你 → 对 脚本执行证据 → 在脚本第一行放 send('alive') 并用 -f spawn → 结果通过是 host 端立刻收到 alive；收不到就是注入层断了，此层以下的所有判断都不作数。
  4. 第四层 脚本 → 你 → 对 目标类与方法 → 打印 ClassLoader 列表、确认类已加载、用 overload 指定签名 → 结果通过是能打印出方法签名，且命中计数大于零。
  5. 第五层 目标逻辑 → 你 → 对 hook 位置 → 查 JIT 内联、查抽取型壳的回填时机、查 native 实现 → 结果是终于允许改业务逻辑，而且此时只动一处。
  6. 每层收尾 → 你 → 对 本层结论 → 写一行「通过 / 卡住 + 依据」→ 结果是二十分钟后你手上有一份可复用的排查记录，而不是一堆改乱的脚本。

每层「看到什么算通过」

  • 连接层：adb devices 显示 device 而非 offline / unauthorized；adb shell echo ok 原样回显。
  • server 层：ps -A | grep frida 有进程，adb forward --list 有 27042 规则，frida-ps -U 能列出目标包名与 pid。
  • 注入层：send('alive') 在 spawn 后一秒内到达 host；没有它，后面所有「值不对」的讨论都是空谈。
  • 脚本层：Java.enumerateClassLoaders 能枚举出目标加载器，overload(...) 打印的签名与 jadx 里一致，命中计数 ≥ 1。
  • 逻辑层：同一输入在不 hook 与 hook 两种状态下结果可对照，且差异能由你改的那一处唯一解释。
  • 内核层补充：dmesg 里若有新 avc 或 -ENOENT / -EINVAL / -ENOSPC，先读它再改代码，比猜快十倍。

可复现实验：一条脚本跑完五层

host 端排错脚本（逐层看输出，卡住即停）
PKG=com.example.range
 
echo '--- L1 连接 ---'
adb devices && adb shell echo ok
 
echo '--- L2 server / 端口 ---'
adb shell ps -A | grep -i frida
adb forward --list
frida-ps -U | grep $PKG
 
echo '--- L3 注入证据 ---'
# probe.js 内容只有一行：send({tag:'alive'})
frida -U -f $PKG -l probe.js --no-pause --runtime=v8 | head -5
 
echo '--- L4 脚本层（类是否加载）---'
# Java.perform(() => Java.enumerateClassLoaders({onMatch: c => send(''+c), onComplete:()=>{}}))
 
echo '--- L5 只读日志，最后再看 ---'
adb shell dmesg | tail -30
adb shell 'dmesg | grep -i avc | tail -10'

看到什么算成功：脚本在某一层给出唯一异常，你停在那一层、修完重跑该层即通过，且没有动过下一层的任何代码。看到什么算失败：五层全绿但现象照旧——这通常意味着你以为在跑的脚本根本不是刚改的那份（缓存、端口转发到了另一台设备、或者 -l 指到了旧路径），先用 ls -l 与 sha256sum 核对文件，再回 L3 重放 alive；还有一种常见情况是热启动掩盖了冷启动缺陷，am force-stop 后完整重跑一次再下结论。

要点
这章最反直觉的一点：九成的「玄学问题」不是代码写错，是你以为在跑的那份代码根本没被加载。缓存、旧端口转发、指向另一个目录的 -l、热启动残留的进程，都会让你对着一份没生效的脚本反复调优。所以 send('alive') 不是调试小技巧，它是整条排错链的地基：先证明「它在跑」，再谈「它跑得对不对」。

一页收尾：四条不许破的规矩

  • 先读日志，再改代码：dmesg、logcat、host 端 error，三处里通常已经写着答案。
  • 一次只改一处：改完立刻重跑同一套用例，否则现象一变就失去归因能力。
  • 每次都留回归：修好之后 am force-stop 冷启动再跑一遍，确认差异只由那一处引起。
  • 先分类，再动手：A01 的速查卡负责定层，本页负责定顺序，两者配合才不会在着急时同时改三处。
