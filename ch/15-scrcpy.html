Android 自动化

u2、scrcpy 与事件驱动核心

稳定的自动化，靠的不是点得准，而是等得对。

15.1 两条并列的通道，不是一条链

这里要先纠正一个常见的画法：uiautomator2 与 scrcpy 不是“串联”关系，而是两条各自独立的通道。u2 走的是 UiAutomation / Accessibility，读的是“窗口树”；scrcpy 走的是 MediaCodec 编码 + adb 传输，拿到的是“像素”。它们互不依赖，可以只用其中一个，也可以同时用。

通道底层机制你拿到什么适合做什么
u2（控件通道）UiAutomation / AccessibilityService控件层级、文本、可点击性按语义定位与点击
scrcpy（画面通道）MediaCodec 编码 + adb 传输 + input 注入视频流、画面像素看屏、录制、处理自绘 UI
adb input（事件通道）直接注入输入事件无（只有动作）无控件信息时的兜底

所以真实的自动化架构是“脚本层 + 两条可选通道”，而不是“脚本 → u2 → scrcpy → App”这样一条链。把这两条通道混成一条链，会导致一个典型设计错误：以为“u2 拿不到控件信息时，scrcpy 也一起挂”——实际上画面通道照样能用。

反过来，两条通道也各有盲区：u2 读不到自绘视图（Canvas / OpenGL 画出来的东西没有控件节点），scrcpy 不知道“这个按钮叫什么”。这正是它们要并列使用的原因。

15.2 三段式：等待 → 动作 → 断言

  1. 等待条件：不要 sleep(2)。要 wait(until=元素出现)，超时才算异常。
  2. 动作：click / set_text / 手势。优先用 resourceId，避免坐标。
  3. 断言：页面签名（关键元素集合）变化才算成功，否则回退重试。
不会“随机失败”的流程骨架
for step in flow:
    el = wait(step.selector, timeout=8)
    if not el:
        retry_or_abort(step)
        continue
    act(el)
    assert_page(step.expect)   # 用元素集合判断，而不是截图比对

15.3 三个实战技巧

  • 页面签名：用“本页必然存在的 3~5 个元素”组成一个集合，全部命中才算到页。比截图比对稳定得多。
  • 幂等重试：每个动作都要能在“已经完成”的状态下安全重跑，否则重试会放大错误。
  • 状态机而非线性脚本：把流程写成状态迁移，异常时能回到上一个稳定态，而不是从头再来。
要点
避坑：不要用“固定等待 + 坐标点击”的组合。这类脚本在开发者手里能跑，换台设备就全废。自动化真正的门槛不是写脚本，而是设计“可恢复”的流程。

15.5 深入：uiautomator2 的两次 dump 有差异怎么办

UI 在动的时候，两次 dump 的结果天然不同。直接比对会得到大量假差异。解决办法是“稳定化”：先等页面静止（连续两次 dump 一致），再做比对。

稳定化等待
def stable_dump(d, tries=5):
    prev = None
    for _ in range(tries):
        cur = d.dump_hierarchy()
        if cur == prev: return cur
        prev = cur
        time.sleep(0.3)
    return prev      # 兜底：返回最后一次

15.6 四种定位方式的可靠性排序

方式可靠性适用
resourceId最高绝大多数控件
text / content-desc中按钮、标签
坐标最低画布类、游戏
xpath / 层级路径中低结构稳定的页面
要点
经验：一个页面里 80% 的控件能用 resourceId 定位，剩下的用 text 兜底。只有真正没有语义信息的控件（如自绘视图）才用坐标，并且必须配合“截图校验”。

15.7 失败重试的正确姿势

  1. 区分失败类型：找不到元素（环境问题）vs 点了没反应（业务问题）。
  2. 限制重试次数：3 次足够，多了只是在浪费时间和放大副作用。
  3. 每次重试前回到已知状态：按返回键、重新拉起页面，而不是在原地瞎点。
  4. 记录现场：截图 + 层级 dump + 当前 Activity 名，比任何日志都有用。

15.8 原理推演：为什么“等”比“点”难

点击是“瞬时动作”，等待是“状态判断”。前者只需要坐标或控件，后者需要“定义什么叫准备好了”。而“准备好了”这件事，在异步 UI 里没有标准答案。

判断方式可靠性实现成本
固定 sleep低最低
元素存在中低
元素可点击较高中
页面签名稳定高中
业务状态断言最高高

工程上建议“多层组合”：先用“元素存在”快速过，再用“页面签名”确认，最后用“业务状态”兜底。只靠一层，必然在某个场景下失效。

15.9 数据细节：一次 dump 的成本

操作耗时说明
dump_hierarchy100~500ms与控件数量强相关
截图50~200ms与分辨率相关
点击20~80ms含事件注入
启动 App1~3s冷启动

这组数字的意义：如果你的轮询间隔小于 dump 的耗时，就会“越等越慢”。正确做法是“指数退避”：先 100ms，再 200ms、400ms，上限 2s。

一条会自己找路的流水线

深夜两点，脚本在第一百台设备上跑挂了：前九十九台都点到了那个按钮，这一台卡在「元素没出现」然后一路重试到超时。把日志翻出来，页面其实早就到了，只是那台机器动画慢了 300 毫秒。稳定的自动化，靠的从来不是点得准，而是等得对——要修的不是坐标，是那句写死的 sleep(2)。把一次点击拆成「等待 → 动作 → 断言」三拍，这条流水线就能自己找路。

还有一件事得先摆正：uiautomator2 读的是窗口树，scrcpy 拿的是像素，这是两条各自独立的通道，不是一条链。u2 挂了，画面通道照样能录屏、能截图、能靠 adb input 兜底；反过来，自绘界面里 scrcpy 看得见按钮，却不知道它叫什么。把它们画成串联，是这类脚本最常见的架构错误。

一次点击，三拍各做了什么

  1. 等待 → 对 UiAutomation 的窗口树 → 轮询 resourceId 或 text 直到命中，或超时 → 结果：拿到的不是「两秒后的屏幕」，而是「元素确实出现了」这个确定事件。
  2. 动作 → 对命中的控件节点 → click() / setText()，必要时退回 adb input tap → 结果：动作作用在语义对象上，换分辨率也不偏。
  3. 断言 → 对下一页的「页面签名」（3~5 个必然存在的元素集合）→ 全部命中才算迁移成功 → 结果：能区分「点了」和「点对了」，失败时知道该回退到哪个稳定态。
  4. 异常恢复 → 对状态机 → 超时就按返回键 / 重新拉起页面，回到上一个已知状态再重跑 → 结果：重试是幂等的，不会把已经填过的表单再填一遍。
  5. 留现场 → 对失败点 → 截图 + dump_hierarchy() + 当前 Activity 名一起落盘 → 结果：第一百台设备那 300 毫秒，下次一眼就能看出来。

动手：把 sleep 换成会等的版本

一个不会随机失败的流程骨架（uiautomator2）
import uiautomator2 as u2, time
 
d = u2.connect()                       # 或 u2.connect('设备序列号')
d.app_start('com.target.app')
 
def wait(sel, timeout=8):
    end = time.time() + timeout
    while time.time() < end:
        el = d(**sel)
        if el.exists:
            return el
        time.sleep(0.2)
    raise RuntimeError('wait timeout: ' + str(sel))
 
def page_sign(names):
    return {n: d(resourceId=n).exists for n in names}
 
login = {'resourceId': 'com.target.app:id/btn_login'}
el = wait(login)                       # 第 1 拍：等事件，不是等时间
el.click()                             # 第 2 拍：作用在语义节点
assert all(page_sign(['com.target.app:id/tv_home',
                      'com.target.app:id/tab_bar']).values())   # 第 3 拍
print('flow ok')

成功：打印 flow ok，且把设备动画速度调慢（adb shell settings put global window_animation_scale 3）后依然通过——这说明脚本等的是元素而不是固定秒数。失败按三类分：RuntimeError: wait timeout 是元素真没出现，先 d.dump_hierarchy() 看是不是页面走岔了，别急着加长超时；assert 挂了说明点到了但没跳到预期页，检查页面签名里是不是混进了非必然元素；而 u2.connect() 报连接失败，跟脚本逻辑无关，先 adb devices 确认设备在线、再确认 atx-agent 还活着。测完记得把动画缩放调回 1。

现象根因该改哪一拍
慢设备上偶发失败固定 sleep / 坐标点击等待：改成 wait(selector)
点了但断言挂页面签名混了非必然元素断言：只留 3~5 个必然元素
重试后表单重复提交动作不幂等恢复：回已知状态再重跑
u2 拿不到控件但屏幕可见自绘视图无控件节点换 scrcpy 画面通道 + 截图校验
自绘界面能点、不知按钮名画面通道没有语义并列用 u2 读树 / 用 OCR 兜底
要点
最反直觉的一点：「找不到元素」时最不该做的，就是把超时调大。绝大多数超时不是等得不够久，而是页面根本走岔了——调大超时只会让错误晚几秒发生，还会把整批任务拖慢。正确动作是立刻 dump 层级 + 截图，先确认「我在哪一页」，再决定是回退还是重来。自动化的门槛从来不是写脚本，是设计可恢复的流程。

这套「等待 → 动作 → 断言 → 恢复」的第 16 章会被直接借走：那里把「页面签名」换成「输出样本」，用同样可证伪的思路去验证一个算法结论；第 13 章的 Binder 通道是 UiAutomation 与 App 之间真正的通信底座；而第 11 章反复强调的「先采基线再差分」，在这里就是那张「页面静止后连续两次 dump 一致」的稳定化条件。
