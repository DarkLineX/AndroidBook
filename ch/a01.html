说人话

这一页不是用来“读”的，是用来查的。

它的组织方式不是按章节，而是按“我现在遇到的是什么问题”：启动起不来查哪一行、hook 不生效查哪一行、脱壳脱不出来查哪一行。找到那一行，它会告诉你结论和对应的章节号。

用它的正确姿势：出问题时先来这里定位“大概在哪一层”，再跳过去看细节。别从头读。

凌晨两点，你不想翻六十五章

凌晨两点，实验又崩了。终端里一行红字，你明知道这本书里讲过，但完全想不起在第几章。这时候按目录从头翻是最慢的做法——六十五章、二十来万字，等你翻到那一页，思路早凉了。真正需要的是一张按「症状」而不是按「章节」组织的卡：先判断这件事发生在哪一层，再决定敲哪条命令。前面 A.1 到 A.4 已经把关键结论按主题压缩过一遍，这一页补的是反过来用的那一条路：从现象倒推层。

把这张卡打印出来贴在显示器边上。它不解释原理，只回答三个问题：现在最可能是哪一层、第一条该敲的命令是什么、看到什么算排除。原理留给正文，卡只负责让你在两分钟内从「不知道」走到「有方向」。

五层倒推，一拍一拍定位

  1. 你 → 对 现象 → 先问「进程还在吗、adb 还通吗」→ 结果是先排除连接层；这一层不过，后面所有判断都建立在空基础上。
  2. 你 → 对 连接层 → 敲 adb devices 与 adb shell getenforce → 结果是确认设备在线、SELinux 状态，顺手把「权限类」问题从候选里划掉或坐实。
  3. 你 → 对 注入层 → 敲 frida-ps -U，再让脚本 send('alive') → 结果是区分「server 没起 / 端口没转发 / 脚本根本没执行」三种完全不同的故障。
  4. 你 → 对 运行时层 → 打印 ClassLoader 与目标类名，确认类真的被加载 → 结果是排掉最隐蔽的一类：Java.use 找错了加载器。
  5. 你 → 对 内核层 → 读 dmesg 里新增的 avc 与错误码 → 结果是 -ENOENT / -EINVAL / -ENOSPC 各自指向符号、参数、槽位，不用猜。
  6. 你 → 对 结论 → 把命中的那一层写进实验笔记 → 结果是下次同类故障直接跳到那一步，卡越用越短。

三层各探一次，把故障锁在一层

三分钟定位脚本（host 端，逐条看输出）
# 1. 连接层：设备在线 + SELinux 状态
adb devices && adb shell getenforce
 
# 2. 注入层：server 活着 + 脚本真的执行了
adb forward tcp:27042 tcp:27042
frida-ps -U | head -20
frida -U -f com.example.range -l probe.js --no-pause  # probe.js 首行 send('alive')
 
# 3. 内核层：只读地看最新日志，别一上来改代码
adb shell dmesg | tail -40
adb shell 'dmesg | grep -i avc | tail -20'

看到什么算成功：上面三组里恰好有一组给出明确异常（设备 offline、frida-ps 空、alive 缺失、dmesg 有新的 avc），你据此把故障锁在单层，并且能用一句话说出「所以下一步该修哪儿」。看到什么算失败：三组全绿但现象照旧——那说明问题在目标逻辑本身（hook 了错的重载、方法被 JIT 内联、dump 时机不对），此时别再往上查环境，直接回到 A05 的排错手册按 Hook 类逐项走。

症状（倒推入口）最可能的层第一条命令排除标准
adb 设备 offline连接层adb kill-server && adb devices状态变 device
frida-ps -U 无输出注入层adb forward + frida-ps -U能列出目标 pid
脚本加载但无回调运行时层send('alive') + 打印 ClassLoaderalive 出现且类命中
偶发崩溃 / SIGILL运行时层缩小 hook 范围、查 BTI 对齐不再复现
模块加载 -ENOENT内核层grep EXPORT_SYMBOL / kallsyms符号存在且导出
加载后立即崩内核层先只做只读观测只读路径稳定
冷启动才复现工程层force-stop 后完整重跑三次结果一致
要点
这章最反直觉的一点：速查表的价值不在「快」，在「逼你先分类再动手」。人一着急就会同时改三处，改完现象变了却不知道是哪一处起的作用；一张按层组织的卡强迫你一次只排除一层，于是每次失败都真的减少了搜索空间。快是副产品，可证伪才是主功能。

一页纸的携带版

  • 启动链：boot.img 五段 → AVB → init → zygote → App → linker，卡住就问「断在第几棒」。
  • Hook 三型：GOT 只拦跨 so、Inline 要顾指令边界与 BTI、Java hook 记得 deopt 内联。
  • 注入六观测面：状态 / 映射 / 账本 / 线程 / 字符串 / 时序；差分检测看的是它们之间的关系。
  • 内核三件：cred 是权限真相、所有改动落到 PTE、KASLR 只平移不改相对偏移。
  • 验证八项：基本 Hook、冷启动、full GC、时延、回归、哈希、备份、已知限制清单。
  • 三条原则：先建模型再记细节；每个结论配一个可证伪实验；改完必须用同一套用例回归。

这张卡和 A02 的术语表是一对：卡告诉你该敲哪条命令，术语表告诉你日志里那个缩写到底指结构、动作还是状态。真到了「命令都对、就是没输出」的时候，直接翻到 A05——那里把这张卡摊开成了五层二分的排错手册。
